# RFC 0001: Tether Protocol

**Category:** Communications
**Status:** Candidate under Revision (v1.0.1)
**Date:** 02026-04-02

## Abstract

Tether is a connection-oriented, datagram-agnostic transport protocol designed for finite, cryptographically addressed sovereign networks. It rejects the Open World Assumption and the "Coordination Trilemma" of the legacy IP stack.

Tether treats **Identity** as an absolute cryptographic commitment derived from public keys, and **Latency** as a physical property to be endured rather than "optimized away".

The protocol operates identically across datacenters, small LANs, and deep-space links, using a fixed, branchless 64-byte header to ensure deterministic processing in all reference frames.

## 1. Introduction

The legacy system ("The Internet") assumes a network of unknown capacity and ephemeral identity. This forces a reliance on heuristics like "Slow Start" which fail completely in deep-time/interplanetary contexts.

Tether assumes a **Finite Universe**:
* **Capacity is Explicit:** Transfers **MUST NOT** occur without pre-allocated **Grants**, unless explicitly flagged as emanating from **Lamps**.
* **Identity is Permanent:** Addresses are 48-bit truncated hashes of Ed25519 Public Keys.
* **Time is Absolute:** All frames carry **TAI64N** timestamps to maintain causal ordering across relativistic distances.

## 2. Terminology

* **Node:** An endpoint identified by a 48-bit `IdentityID`.
* **Flow:** A logical stream of data within a session.
* **Spine:** The default gateway for any traffic with an unknown destination.
* **Registry:** The source of truth for name/alias -> `IdentityID` resolution.
* **Grant:** A value carrying the number of **Bytes** the Receiver is authorized to send.
* **Slot:** Represents the index of the chunk in the Flow.
* **Lamp:** A speculative transmission sent without prior Grant, carrying sufficient credits to fund a reply.

## 3. Physical Layer & Addressing

Tether frames **MUST** be standard IEEE 802.3 Ethernet frames.

### 3.1 EtherType

Tether uses the "Experimental" EtherType **0x88B5**.

### 3.2 Addressing Scheme

All addresses **MUST** be 48-bit MAC addresses:
* **Unicast Identity:** `AC:1D:xx:xx:xx:xx`. Derived from `Truncate(BLAKE3(Ed25519_PubKey), 6)`.
* **Multicast Group:** `AD:1D:xx:xx:xx:xx`.
* **The Spine:** `CC:CC:CC:CC:CC:CC`.
* **The Registry:** `AC:1D:00:00:00:00`.

## 4. Header Format

Tether utilizes a fixed 64-byte header designed for branchless processing. All fields are evaluated for every packet.

### 4.2 Field Semantics

* **Magic:** `0x4F424F4C` ("OBOL").
> Asserts intelligent origin. Honors the Ferryman.
* **Flags:**
> `0x01` (**LAMP**): **Lamp Mode**. The Sender asserts this packet is sent without a Grant. The Receiver **MUST NOT** deduct credits, but **MAY** drop the packet if resource-constrained or covert.
> `0x02` (**SYNC**): A request for time/state alignment.
* **FlowID:**
> `0`: **Control Plane**. **MUST** be processed with highest priority. Payload is defined in Appendix A.
> `1..65535`: **User Streams**. Payload is raw data mapped to the `SlotID`.
* **SlotID:** The index of the memory chunk this packet belongs to.
> `PhysicalOffset` = `SlotID` * `SlotSize` (Defined in Flow 0).
* **GrantAmount:** The number of **Bytes** the Sender authorizes the Target to transmit back.
* **NackSlot (Singleton Error):** If non-zero, the Sender asserts that **this specific** `SlotID` is missing. Optimization for high-reliability local networks.
> For multi-packet loss, use the **Bulk NACK** mechanism (see 5.3).
* **Checksum:** `CRC64-ISO` of the entire frame (Header + Payload). During calculation, this field **MUST** be assumed to be **zero**.

## 5. Transport Logic

### 5.1 Processing Loop

Upon receipt, the Node **MUST** perform these operations:
* **Integrity:** Verify CRC64-ISO. Abort or NACK on failure according to local policy.
* **Auth:** Validate `SenderID` against AllowList/Cache.
* **Flow Update:** `LocalCredits[FlowID] += Header.GrantAmount`.
* **Singleton Error-Handling:** If `Header.NackSlot != 0`, mark `NackSlot` for retransmission.
* **Payload Handling:**
    * If `FlowID == 0`: Process Control Payload (See Appendix A).
    * Else: DMA payload to memory region associated with `SlotID`.

### 5.2 Connection & Discovery (Lamps)

To initiate contact without prior arrangement (e.g., Deep Space "Cold Start"):
* `Lamp`: Initiator sends Frame on **Flow 0**:
> `Flags`: **LAMP** (`0x01`)
> `Grant`: **128** (Payment for the reply header and a spare)
> `Payload`: `ControlHeader { op: Hail, ... }`

* **Reception:** Target receives the Lamp's message. If policy allows, Target creates a Flow Entry.
* **Reply:** Target replies on **Flow 0**:
* `Grant`: **4096** (Arbitrary, invitation to continue)
* `Payload`: `ControlHeader { op: Hail, ... }` (Empty Ack)

The Target has consumed **64 bytes** of the Initiator's 128-byte Grant to transmit this header. The remaining 64 bytes are available for immediate negotiation.

**The connection is now mutually funded, the receiver's existence is revealed.**

### 5.3 Standard Flows

Before sending data, the Sender defines the "Flow Geometry" on **Flow 0** via the `Define` payload.

* **Message:** `Define(target_flow: 42, total_bytes: 1000GiB, slot_size: 64KiB)`

**Tethered Mode (Terrestrial):**
* Receiver: "We have 16GiB of RAM free." Sends Header with `GrantAmount = 16GiB`.
* Sender: Sends 16GiB at maximum line rate.
* Receiver: Drains the buffer, sends more Grants. **No Slow Start.**

**Lamp Mode (Deep Space):**
* Sender: "We will never live to receive a response."
* Sender: Sets `LAMP` (`0x01`) flag.
* Sender: Sends `Define` payload.
* Sender: Immediately redundantly transmits `SlotID 0...N`.
* Sender: Sends `Manifest` payload at the end to report on transmission costs.
* Receiver: Decides whether to buffer or ignore, based on internal policy.

### 5.4 Error Recovery Modes

* **Singleton:** For single dropped packets, the Receiver sets the `NackSlot` field in the very next outgoing header. This consumes zero payload space.
* **Bulk:** If multiple gaps are detected, the Receiver sends a **Flow 0** packet containing the `Nack` payload, listing the missing `SlotIDs`.

## Appendix A: Control Plane Definition

> The following definitions use the [Haga](https://github.com/wilson/haga) strict configuration syntax.
> Haga is a tiny subset of the Ruby grammar, hence the temporary use of that syntax name for convenience.

* **Types:** `u8`, `u16`, `u32`, `u64` are standard little-endian unsigned integers.
* **Alignment:** All fields are naturally aligned.
* **Padding:** The `reserved` fields **MUST** be zeroed.

### Physical Layout

- All Control Payloads reside immediately after the 64-byte Header.
- All Control Payloads MUST be padded to fill exactly one 64-byte Quantum.

This ensures the total frame size is always a multiple of 64 bytes.

```ruby
scope control_header {
  # "Tag" identifies the structure of the body.
  must "tag", "u32"
  # Padding to ensure the body starts at offset 8 relative to the Quantum.
  must "reserved", "u32"
}
```

### "Tag" Payload Definitions

- These **MUST** begin at Byte "8" of the payload, immediately after the control header.
- The remaining bytes in any 64-byte sequence that is begun, **MUST** be zeroed.

#### Tag 1: Hail (Reveal Sender)
```ruby
scope payload_hail {
  must "version", "u32"
  must "capabilities", "u32"
  # (Implicit padding: 48 bytes)
}
```

#### Tag 2: Define (Flow Geometry)
```ruby
scope payload_define {
  must "target_flow", "u16"
  must "reserved", "u16"
  must "slot_size", "u32"
  must "total_bytes", "u64"
  # (Implicit padding: 40 bytes)
}
```

#### Tag 3: Manifest (Expense Report)
```ruby
scope payload_manifest {
  must "target_flow", "u16"
  must "reserved", "u16"
  must "checksum_lo", "u32"
  must "checksum_hi", "u32"
  must "total_slots", "u64"
  must "total_frames", "u64"
}
```

#### Tag 4: NACK (Bulk Re-transmit Request)
```ruby
scope payload_nack {
  must "target_flow", "u16"
  must "reserved", "u16"
  must "count", "u32"
  # Followed by a dense array of [count] u64 SlotIDs
  some "slots", "u64"
}
```

#### Tag 5: Sideband (Transport-Specific Feedback)
```ruby
scope payload_sideband {
  must "target_flow", "u16"
  must "attention", "u16" # A "sub-identity" the counter-party knows how to reach
  must "count", "u32"
  some "tranche", "u64"
}
```

#### Tag 6: Link Schedule (Availability and/or Duty Cycle)
```ruby
scope payload_link_schedule {
  must "target_flow", "u16"
  must "duration_scale", "u8" # Base 10 inverse exponent on seconds, e.g. 9=nano, 18=atto, 44=Planck
  must "periodic_scale", "u8" # As "duration_scale"
  must "duration", "u32"      # How long the link is available during each period, in the timescale specified
  must "period", "u64"        # How often the link is available, expressed in the timescale specified. (0 indicates a one-off event)
  must "epoch", "u256"        # A TAI256 timestamp in Q112.144 format that the schedule is relative to
}
```
